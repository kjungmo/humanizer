# 프리셋: 개발자 블로그 글 (`dev-blog`)

기술 포스팅, 트러블슈팅 기록, 설계 회고. 읽는 사람은 같은 문제를 겪고 검색해서 들어온 개발자다.

여섯 프리셋 중 `general` 다음으로 원문을 적게 건드린다. 어투를 합니다체로 맞추고 흔적을 지우되, **구조와 분량은 원문을 따른다.** 기술 글은 길어야 할 이유가 있으면 길어도 된다.

## 다이얼

| 항목 | 값 |
|---|---|
| 어투 | 합니다체. 문어체·반말로 들어와도 합니다체로 옮긴다 |
| 분량 | 상한 없음. 원문 구조를 따른다 |
| 이모지 | 금지 |
| 해시태그 | 없음 |
| 구조 | 소제목 + 코드블록. 원문의 절 구성을 유지한다 |
| 훅·CTA | 넣지 않는다. 첫 문단은 무슨 문제를 다루는지로 시작한다 |

## 완화하는 패턴

| ID | 패턴 | 왜 여기서는 정상인가 |
|---|---|---|
| B-1 | 괄호 영어 병기 | 용어를 처음 꺼낼 때 원어를 적어 줘야 검색이 된다 |
| C-9 | 숫자 괄호 인덱싱 | 재현 절차를 (1)(2)(3)으로 세는 게 절차 문서의 문법이다 |
| C-10 | 콜론 부제 헤딩 | "증상: 빌드가 30분 걸립니다" 형태가 훑기 좋다 |
| J-1 | 볼드 남용 | 파일명·설정값·플래그를 굵게 표시하는 관습이 있다 |

B-1은 완화하되 **처음 한 번만이다.** "가비지 컬렉션(garbage collection)"을 한 번 적었으면 그다음부터는 한국어만 쓴다. 매 문단 병기는 이 채널에서도 AI 티다.

## 강화하는 규칙

**1. 코드·명령어·경로·버전 문자열은 한 글자도 바꾸지 않는다.** 스캐너의 보호 구간 마스킹이 탐지에서 빼 주지만, 윤문할 때 손대는 건 사람이다. 코드블록 안 주석의 오타도 그대로 둔다. 원문 그대로여야 복사해서 돌아간다.

**2. 재현 절차가 남아 있어야 한다.** 환경(OS·언어·라이브러리 버전), 증상, 시도한 것, 결과. 원문에 있으면 반드시 살린다. 흔적을 지운다고 "여러 방법을 시도했습니다"로 뭉개면 글의 값어치가 사라진다. **구체가 이 채널의 전부다.**

**3. 실패한 시도를 지우지 않는다.** "A를 해 봤는데 안 됐고, 알고 보니 B가 원인이었습니다"는 사람이 쓴 글의 가장 강한 신호다. AI 글은 정답만 매끈하게 늘어놓는다. 원문에 헛발질이 있으면 그게 자산이다.

**4. 영어 용어를 한국어로 새로 만들지 않는다.** 업계에서 쓰는 말을 쓴다. `deadlock`을 "교착 상태"로 옮기는 건 되지만 `mutex`를 "상호 배제 자물쇠"로 옮기지 않는다. 판단 기준은 그 분야 사람이 실제로 그렇게 부르는가다.

**5. 근거 링크 자리를 남긴다.** 원문에 문서·이슈·커밋 링크가 있으면 그대로 둔다. 없는데 "공식 문서에 따르면" 같은 문장이 있으면 그건 출처 없는 권위 호출(D-9)이다. 링크를 지어내지 말고 그 문장을 지우거나 `[출처 필요]`로 표시한다.

## 이 채널에서 특히 자주 나오는 AI 흔적

- **예고 멘트**(I-4): "이번 포스팅에서는 ○○에 대해 알아보겠습니다". 지운다. 문제부터 쓴다.
- **과장된 의의**(D-8): "○○의 중요성은 아무리 강조해도 지나치지 않습니다".
- **3의 법칙**(C-7): "장점은 세 가지입니다"로 시작해 억지로 셋을 채운다. 둘이면 둘만 쓴다.
- **출처 없는 권위**(D-9): "일반적으로 알려져 있습니다", "많은 개발자들이 사용합니다".
- **개념만 있고 코드가 없음**: 규칙 위반은 아니지만 이 채널에서 가장 확실한 AI 신호다. 원문에 코드가 있으면 반드시 살린다.
- **다짐 마무리**: "앞으로도 꾸준히 공부하겠습니다". 마지막은 결과나 남은 과제로 끝낸다.
- **어투 혼합**(E-7): 설명은 합니다체인데 후기 부분만 "해봤어요"로 새는 경우. 합니다체로 통일한다.

## 가드

**변경률 가드가 유효하다.** 여섯 프리셋 중 `general`과 이 프리셋만 그렇다. 구조와 분량을 원문에서 가져오기 때문이다.

- 변경률 **30% 초과: 경고.** 왜 그만큼 손댔는지 보고에 적는다. 원문이 반말이나 문어체여서 어투 변환이 크게 잡힌 경우가 대부분이다.
- 변경률 **50% 초과: 중단하고 롤백.**

```bash
python3 -m humanizer detect 결과물.md --preset dev-blog
python3 -m humanizer diff 원본.md 결과물.md --preset dev-blog
```

사실 대장은 필수가 아니지만, 버전 번호와 수치가 많은 글이면 뽑아 두는 편이 안전하다. 기술 글에서 `v2.9.1`을 `v2.9`로 흘리는 건 사실 훼손이다.

## 글쓴이 말투가 있으면

```bash
python3 -m humanizer detect 결과물.md --preset dev-blog --voice voice/이름.json
```

개발자 블로그는 말투 프로필이 가장 잘 맞는 채널이다. 개발 메모와 소재가 같아서 표본을 구하기 쉽다.

다만 **메모체를 그대로 블로그에 옮기지 않는다.** 개인 메모는 음슴체와 개조식이 대부분인데, 블로그는 남이 읽는 글이라 합니다체로 간다. 프로필에서 가져올 것은 종결 형태가 아니라 **문장 길이의 분포, 문단을 끊는 습관, 입버릇, 부호 쓰는 버릇**이다. 짧게 치다가 한 번씩 길게 흘리는 리듬이 그 사람의 지문이고, 그건 어투를 바꿔도 남는다.

개인 기준선은 그대로 쓴다. 문두 접속사를 원래 많이 쓰는 사람이면 H-1을 들이대지 않는다.

## 출력 형식

`SKILL.md` 12절 그대로다. 코드블록이 포함된 글이므로 **최종본을 낼 때 코드블록이 원문과 동일한지 눈으로 한 번 더 본다.**

## 예시

**Before (AI가 쓴 트러블슈팅 글):**

> 이번 포스팅에서는 도커 빌드 최적화에 대해 알아보겠습니다. 도커(Docker) 빌드 시간의 중요성은 아무리 강조해도 지나치지 않습니다. 최적화 방법은 세 가지가 있습니다. 첫째, 레이어 캐싱(layer caching)을 활용합니다. 둘째, 멀티 스테이지 빌드(multi-stage build)를 사용합니다. 셋째, 불필요한 파일을 제외합니다. 일반적으로 이러한 방법들을 통해 빌드 시간이 크게 단축되어진다고 알려져 있습니다. 앞으로도 꾸준히 최적화를 공부하겠습니다.

**스캐너:** `I-4`(알아보겠습니다) · `D-8`(아무리 강조해도) · `C-7`(세 가지 나열) · `A-2`(통해) · `A-8`(단축되어진다) · `D-9`(일반적으로·알려져 있습니다) · `A-17`(방법들). B-1 병기는 완화 대상이라 세지 않는다.

**After:**

> CI에서 도커 빌드가 8분 걸리고 있었습니다. 캐시가 매번 깨지는 게 원인이었습니다.
>
> **증상**
> `COPY . .`을 `RUN npm install` 앞에 두는 바람에, 소스가 한 글자만 바뀌어도 그 아래 레이어가 전부 무효가 됐습니다.
>
> **고친 것**
> 의존성 파일만 먼저 복사하고 설치한 다음, 소스를 복사하도록 순서를 바꿨습니다.
>
> ```dockerfile
> COPY package*.json ./
> RUN npm install
> COPY . .
> ```
>
> 빌드는 8분에서 1분 40초로 줄었습니다.
>
> **안 먹혔던 것**
> 멀티 스테이지 빌드부터 손댔는데 이건 이미지 크기만 줄었고 빌드 시간은 그대로였습니다. 원인이 캐시 무효화라 스테이지를 나눠도 소용이 없었습니다.
>
> 남은 건 `node_modules` 캐시를 러너 사이에서 공유하는 부분입니다.

예고 멘트와 다짐 마무리를 지웠습니다. 3항 나열을 실제로 한 일 하나로 줄였고, 안 먹혔던 시도를 절로 남겼습니다. 코드블록은 손대지 않습니다. `8분`, `1분 40초` 같은 수치는 원문에 없던 것이면 **지어내면 안 됩니다.** 이 예시는 원문에 그 수치가 있었다고 가정한 것이고, 없었다면 자리를 비워 표시합니다.
